# 代码审查循环技能

## 技能概述
在每次修改或新增功能后，对代码进行持续审查、发现问题、优化、再审查的循环流程，直到代码质量达标。

## 自动触发条件
此技能会在以下情况**自动触发**：
1. ✅ 使用 Edit 或 Write 工具修改文件后
2. ✅ 完成功能开发后
3. ✅ 修复 Bug 后
4. ✅ 用户明确要求"审查代码"或"检查代码质量"

## 技能定位
你是小边的代码质量守护者，负责在每次代码变更后自动进行多轮审查，确保代码质量。

## 循环流程

```
┌─────────────────────────────────────────────────────────────┐
│                    代码审查循环流程                          │
└─────────────────────────────────────────────────────────────┘

    开始
      ↓
┌─────────────────┐
│  第一步：代码审查 │  ← 读取修改的文件
└────────┬────────┘
         ↓
    发现问题？
      ↓ 是
┌─────────────────┐
│  第二步：问题分析 │  ← 分析问题严重程度和影响
└────────┬────────┘
         ↓
┌─────────────────┐
│  第三步：优化代码 │  ← 修复发现的问题
└────────┬────────┘
         ↓
┌─────────────────┐
│  第四步：验证修复 │  ← 检查问题是否解决
└────────┬────────┘
         ↓
    还有问题？
      ↓ 是
      └──────→ 返回第一步
         ↓ 否
      结束
```

## 第一步：代码审查

### 审查范围
每次修改或新增的文件，包括：
- 新增的功能代码
- 修改的现有代码
- 相关的配置文件
- 类型定义文件

### 审查维度

#### 1. 代码正确性
- [ ] **类型安全**: TypeScript 类型是否正确，有无 `any` 滥用
- [ ] **逻辑正确**: 业务逻辑是否正确实现
- [ ] **边界处理**: 是否处理了边界情况（空值、undefined、null）
- [ ] **错误处理**: 是否有完善的 try-catch 和错误提示

#### 2. 代码质量
- [ ] **命名规范**: 变量、函数、组件命名是否语义化
- [ ] **代码复用**: 是否有重复代码，是否可以抽取
- [ ] **函数长度**: 单个函数是否过长（建议 < 50 行）
- [ ] **复杂度**: 代码逻辑是否过于复杂

#### 3. 性能优化
- [ ] **不必要的渲染**: React 组件是否有不必要的重渲染
- [ ] **内存泄漏**: useEffect 清理是否正确
- [ ] **请求优化**: 是否有重复或冗余的 API 请求
- [ ] **大对象传递**: 是否传递了过大的对象作为 props

#### 4. 安全性
- [ ] **XSS 防护**: 用户输入是否正确转义
- [ ] **敏感信息**: 是否有硬编码的密钥、token
- [ ] **权限控制**: API 调用是否包含必要的权限验证

#### 5. 用户体验
- [ ] **加载状态**: 是否有 loading 提示
- [ ] **错误提示**: 错误信息是否友好
- [ ] **空状态**: 是否处理了空数据情况
- [ ] **响应式**: 是否适配不同屏幕尺寸

#### 6. 代码规范
- [ ] **导入顺序**: import 语句是否按规范排序
- [ ] **注释完整**: 复杂逻辑是否有注释说明
- [ ] **格式统一**: 代码格式是否符合项目规范
- [ ] **未使用代码**: 是否有未使用的变量或导入

### 审查方法
```bash
# 1. 获取修改的文件列表
git diff --name-only HEAD~1

# 2. 读取每个修改的文件
# 3. 逐个检查上述审查维度
# 4. 记录发现的所有问题
```

## 第二步：问题分析

### 问题分级

| 等级 | 描述 | 示例 | 处理方式 |
|-----|------|------|----------|
| 🔴 严重 | 导致功能错误或安全风险 | 类型错误、逻辑错误、XSS漏洞 | 必须修复 |
| 🟡 中等 | 影响代码质量或性能 | 重复代码、缺少错误处理 | 建议修复 |
| 🟢 轻微 | 不影响功能，可优化 | 命名不规范、缺少注释 | 可选优化 |

### 问题记录格式
```markdown
## 问题列表

### 🔴 严重问题
1. [类型错误] 文件位置:行号
   - 问题描述: 具体描述问题
   - 影响: 这个问题会导致什么后果
   - 建议: 如何修复

### 🟡 中等问题
1. [代码质量] 文件位置:行号
   - 问题描述: 具体描述问题
   - 影响: 这个问题的影响
   - 建议: 如何修复

### 🟢 轻微问题
1. [代码规范] 文件位置:行号
   - 问题描述: 具体描述问题
   - 建议: 如何优化
```

## 第三步：优化代码

### 修复优先级
1. **先修复 🔴 严重问题** - 这些问题会导致功能错误
2. **再修复 🟡 中等问题** - 提升代码质量
3. **最后处理 🟢 轻微问题** - 代码优化

### 修复原则
- **最小改动**: 只修改必要的部分
- **保持一致**: 修改后与项目现有代码风格一致
- **测试验证**: 修改后验证功能正常

### 修复方法
```typescript
// 示例1: 修复类型安全问题
// 修改前
const data: any = await fetchData();

// 修改后
interface DataResponse {
  id: number;
  name: string;
}
const data = await fetchData() as DataResponse;

// 示例2: 添加错误处理
// 修改前
const result = await api.call();

// 修改后
try {
  const result = await api.call();
  return result;
} catch (error) {
  console.error('API调用失败:', error);
  void message.error('操作失败，请重试');
  return null;
}

// 示例3: 优化性能
// 修改前
useEffect(() => {
  fetchData();
}, [data]); // data 变化就重新请求

// 修改后
useEffect(() => {
  fetchData();
}, [data.id]); // 只在 id 变化时请求
```

## 第四步：验证修复

### 验证步骤
1. **类型检查**: `npx tsc --noEmit`
2. **代码格式检查**: `npm run lint`
3. **功能测试**: 手动测试修改的功能
4. **回归测试**: 确保没有影响其他功能

### 验证清单
- [ ] TypeScript 编译通过，无类型错误
- [ ] ESLint 检查通过，无警告
- [ ] 修改的功能正常工作
- [ ] 相关功能未受影响
- [ ] 控制台无错误信息
- [ ] 网络请求正常

### 循环判断
```
IF 验证通过 AND 无问题 THEN
    → 审查通过，结束循环
ELSE IF 仍有问题 THEN
    → 返回第一步，继续审查
END IF
```

## 自动化检查命令

### 前端项目
```bash
# TypeScript 类型检查
npx tsc --noEmit

# ESLint 代码规范检查
npm run lint

# 格式化代码
npm run format
```

### 后端项目
```bash
# TypeScript 类型检查
npx tsc --noEmit

# Prisma 类型生成
npx prisma generate

# 数据库迁移检查
npx prisma migrate status
```

## 注意事项

1. **循环次数**: 通常 1-2 轮即可完成，不应超过 3 轮
2. **修复范围**: 只修复本次修改相关的问题
3. **测试覆盖**: 修复后必须验证功能正常
4. **文档更新**: 如果修改了 API，同步更新文档

## 触发时机

- ✅ 新增功能后
- ✅ 修复 Bug 后
- ✅ 重构代码后
- ✅ 代码提交前

**审查原则**: 严谨细致、持续改进、质量优先
